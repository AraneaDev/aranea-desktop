# Agent development guide

Use this guide when changing the repository through automation. Establish the
editing boundary, preserve existing work, verify the relevant contract, and
hand off the exact remaining state. [Agent interface](agent-interface.md)
documents the installed command protocol.

## Start with repository state

```bash
git status --short --branch
git diff --stat
```

Read repository instructions and the task scope before editing. Preserve
unrelated changes and do not reset user work. Use the current branch unless the
task or isolation requirements call for a separate worktree. For cross-cutting
changes, read [Architecture](architecture.md) and [Development](development.md)
first: generated outputs, shared presentation, and live owners have different
responsibilities.

## Choose the correct source of truth

| Change                                        | Edit first                                                                                        | Verify                                  |
| --------------------------------------------- | ------------------------------------------------------------------------------------------------- | --------------------------------------- |
| Palette, dimensions, typography, motion       | `design/tokens.toml`                                                                              | Token generator write/check             |
| CSS, shell, or asset projection               | `design/templates/`                                                                               | Token generator write/check             |
| Identity geometry                             | `branding/marks/aranea-primary.svg`, with derived assets generated by `tools/token-generator.mjs` | Generated mark/assets and visual review |
| Facade behavior                               | Focused sibling JavaScript module                                                                 | Direct tests and facade generator       |
| Repeated QML presentation                     | `plugins/araneadev.shared/`                                                                       | `qmldir` registration and QML fixtures  |
| Plugin lifecycle, IPC, or operation ownership | Owning plugin                                                                                     | Behavior/flow tests                     |
| Install, repair, or persistence               | `scripts/`, `hooks/`, `tools/`                                                                    | Shell and JSON contracts                |

Never hand-edit generated projections or facade regions. Fix the source or
renderer if their diffs are wrong. Identity is fixed; palette customization
remains in the token source.

## Extract and deduplicate safely

Shared QML needs a stable repeated contract: explicit properties, action signals,
token defaults, and no root-only IDs. Keep filtering, persistence, cursor state,
IPC, and process ownership with the host. Use `RuntimePaths.qml` for shared
paths, preserving intentional lock-screen path behavior.

Pure JavaScript modules normalize or calculate. Extract one domain at a time,
preserve exported facade names, add direct tests, and regenerate. Do not move
window lifecycle or I/O into those modules.

For project and activity work, distinguish accepted submission, observed runtime
identity, reported state, and verification. A closed window or disconnected
observer does not cancel an accepted operation. Review recovery paths for stale
sessions and partial outcomes before adding automatic retry.

## Test-driven change loop

1. Identify the behavior and stable contract.
2. Add or update the narrowest useful contract test.
3. Make the change and inspect generated/source diffs.
4. Run focused checks, then related suites.
5. Run the canonical gate before claiming implementation completion.

```bash
tests/run menu
node --test tests/js/menu-guards.test.js
tests/qml-types.test.sh
tests/qml-behaviour.test.sh shared
tools/check
```

For documentation-only edits, run formatting, Markdown lint, links, and diff
whitespace checks. Report the exact failed command and reproducibility. Do not
weaken a baseline to obtain a green result; fix the cause or identify the
unavailable host dependency. A skipped runtime check is not a pass.

## Isolated screenshot sessions

Select an intentionally empty workspace 2 before the public batch:

```bash
scripts/capture-screenshots --all --output screenshots
```

Workspace 2 stays pinned. The script parks/restores the notification inbox,
stages device/provider names, and returns to workspace 1 after capture. Captures
preserve the real Usage provider; the Codex fixture does not save that preference.
Use `omarchy-shell omarchy.agents select codex` only to intentionally change the
real provider. See [capture details](development.md#showcase-captures), including
notification arrival handling and rendered surfaces.

For a separately staged shell, run both shell and capture commands through:

```text
tools/with-capture-session COMMAND [ARGS...]
```

The helper creates a private D-Bus bus, runtime directory, and document data
area, sharing only the Wayland display socket. It stops private capture process
groups before cleanup. The caller stages shell configuration. This is capture
session separation; it does not restart the user's shell or change workspaces.

Do not run `dbus-run-session` with the live `XDG_RUNTIME_DIR`: another document
portal can unmount the live document filesystem. Keep live `doc`, `at-spi`,
`bus`, and `systemd` paths outside the private runtime. The public script also
refuses tray captures with real registered tray apps.

## Documentation and review handoff

Update the closest guide for changed behavior, ownership, commands, or recovery.
Use Architecture for ownership and Agent interface for protocol changes. Verify:

```bash
git diff --check
git status --short --branch
tools/check
```

Report the result, relevant validation, unavailable host checks, and uncommitted
work. Scope the claims to checks actually run.

Release work follows [Contributing](../CONTRIBUTING.md#releases): conventional
commits reach verified `master`, release-please opens or updates its PR, checks
pass, then merging that PR creates the version tag and release. Docs-only pushes
are excluded from its push trigger; explicit workflow dispatch can run it.
